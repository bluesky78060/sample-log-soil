# SLS-1-269 플랜 리뷰

- 리뷰어: **codex (codex-cli 0.147.0)** — 독립 레인
- 일시: 2026-08-21 · 판정: **APPROVED (지적 반영 후)**

## 반영한 지적

| # | 지적 | 반영 |
| --- | --- | --- |
| 1 | 프로세스 테스트를 **2건** 남기는 편이 안전하다. 1건만 남기면 "실패 종료 계약만" 검증하는 것이고, CLI가 아예 안 도는 회귀를 놓친다 | 16(실패 종료) + **16-b(성공 CLI)** 두 건으로 남겼다. 플랜 문구도 "CLI 계약"에서 "실패 종료 + 성공 실행"으로 좁혔다 |
| 2 | 테스트 파일이 ESM이라 `require`가 그대로 되지 않을 수 있다 | `createRequire(import.meta.url)` 사용 |
| 3 | `dom.window.close()` 없이 반복 호출하면 누수 | `try/finally`로 닫는다 |
| 4 | `extract()`의 실패 처리 범위를 명확히 | **알려진 검증 실패만** `{ok:false}`, 파일 권한·JSON 파싱 오류는 **그대로 던진다**(주석 명시) |
| 5 | "jsdom을 한 번만 로드"는 **모듈 로드** 비용에 대한 표현. `new JSDOM()`과 HTML 파싱은 호출마다 계속 발생 | 주석·문서 문구 정정 |
| 6 | 변이 (a)는 현재 테스트로 실패가 보장되지 않는다. 저장소 오염 검증을 추가해야 한다 | **아래 참조 — 실제로 두 번 틀렸다** |
| 7 | 경로 3곳(`RELEASE_HTML`·`OUT_FILE`·`package.json`) 완전 인자화 | 전부 `root` 기준으로 계산 |

## 지적 6이 두 번 옳았다

**첫 번째** — 변이 (a)(`require.main` 가드 제거)를 걸고 돌리니 **11건 전부 통과**했다.
가드가 없으면 테스트가 `require`하는 순간 저장소의 `src/shared/whatsnew-data.js`가
덮어써지는데, **아무 테스트도 잡지 못했다.** SENTINEL을 심어 수동으로 확인해야 보였다.
→ 테스트 18을 신설했다 (자식 프로세스에서 `require`만 시키고 산출물을 확인).

**두 번째** — 테스트 18의 초안은 **파일 내용을 비교**했는데 변이가 또 살아남았다.
재생성해도 **결과가 같아서** 문자열이 일치한다. → **수정 시각(`mtimeMs`)** 비교로 바꿔
비로소 변이 (a)가 죽었다.

> 교훈: "덮어썼는가"를 내용 동일성으로 판정하면 **멱등한 쓰기를 놓친다.**

## 측정으로 확인된 원인 (티켓 요구사항)

| 측정 | 값 |
| --- | --- |
| node 기동만 | 23 ms |
| node + `require('jsdom')` | 235 ms |
| 테스트 1건 (부하 없음) | 297~381 ms |

비용의 약 75%가 **jsdom 모듈 로드**이고 그것을 테스트마다 새 프로세스에서 다시 냈다.
성능 회귀가 아니라 **구조**다. 그래서 타임아웃 상향으로 덮지 않았다.

## 리뷰어가 확인해 준 것

- vitest environment는 `jsdom`, pool 기본값은 `forks`. in-process 전환과 충돌 없음
- 변이 (b)(c)는 유효하다
- 16번을 subprocess로 남기는 선택은 **타당한 최소선**이다

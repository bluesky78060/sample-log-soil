# SLS-1-223 플랜 리뷰

## ⚠️ 플랜 리뷰를 수행하지 않았다 (정직한 기록)

`critic` 에이전트 플랜 리뷰를 **실행하지 않았다.** 사유: 사용자 지시 — "코드 수정이나 중요가 낮은 작업은 플랜리뷰하지말고 진행해줘".

## 생략을 정당화하는 근거

| 근거 | 내용 |
| --- | --- |
| 결함·원인·경로가 이미 확정 | SLS-1-222의 코드 리뷰와 적대적 검증이 재현까지 마쳤다 |
| 핵심 변경이 정상 데이터에서 no-op | B(표기 기준 네임스페이스)는 불변식이 지켜지는 레코드에서 구/신 결과가 같다. 속성 테스트로 증명한다 |
| 기존 패턴을 따른다 | 탐지 UI는 설정 화면의 유지보수 도구(`migrateAllBtn`·`purgeYearsBtn`·`clearCacheBtn`)와 같은 형태 |

## 그래도 남는 리스크와 대응

1. **B가 채번 규칙 변경이다** — 폼 등록·가져오기 양쪽에 영향. → 정상 데이터 no-op을 **속성 테스트**로 증명하고, 위반 데이터에서만 달라짐을 별도로 단정한다. 구 구현을 테스트에 복사해 대조한다.

2. **C가 정당한 수정을 막을 수 있다** — 구분만 고치려는 사용자가 접수번호까지 바꿔야 한다. 자동 재부여는 접수번호가 이미 라벨에 인쇄됐을 수 있어 더 위험하다. → **차단 + 명확한 안내**를 택하고 이 판단을 리뷰와 사용자 확인에 올린다. 되돌리기 쉬운 형태로 만든다.

3. **검증 축이 하나뿐이면 또 놓친다** — SLS-1-222의 교훈. → "대장 전체에 중복 0"과 "정상 데이터 no-op"을 **독립 축 두 개**로 둔다.

4. **손상 데이터 재번호를 하지 않는다** — 운영 데이터를 코드로 볼 수 없고 담당자 판단이 필요하다. → A(탐지)만 제공하고, 재번호 여부는 탐지 결과를 보고 사용자가 결정한다. 이 사실을 완료 보고에 명시한다.

## 코드 리뷰와 적대적 검증은 생략하지 않는다

SLS-1-222에서 **코드 리뷰 APPROVED 뒤 적대적 검증이 결함을 찾았다.** 같은 순서로 진행한다. 생략한 것은 플랜 리뷰뿐이다.

## E2E가 설계를 바로잡았다 — 되돌리는 것이 오히려 방해가 되는 경우

첫 구현은 "언제나 보던 자리를 지킨다"였다. E2E가 그것을 깨뜨렸다.

**맨 왼쪽에서 전체 보기를 켜면 스크롤이 150px 밀려 사용자가 보려던 바로 그 열
(경지구분·우편번호)이 화면 밖으로 나갔다.** '전체 보기'를 누르는 목적이 숨은 열을
보는 것인데, 보정이 그 목적을 정면으로 방해한 것이다.

되돌릴 자리가 없는 쪽에서는 되돌리지 않는다.

> 💡 이 결함은 **기능이 의도대로 동작할 때** 드러난다. 보정 자체는 정확했고,
> 정확했기 때문에 문제가 됐다. 시험이 "값이 맞나"가 아니라 **"사용자가 보려던 것이
> 보이나"**를 물었기에 잡혔다.

## codex MINOR — 왼쪽 경계가 너무 좁다 · **반영**

**재현**: `scrollLeft = 1`에서 전체 보기를 켠다. `=== 0`만 예외로 두면 보정이 걸려
**스크롤이 약 151px로 튄다.** 좌측 끝 근처에서 보려던 새 열이 다시 화면 밖으로 밀린다.

**반영**: 경계를 `shift`로 바꿨다 — **새로 나타난 열이 차지한 폭**이다.

```js
if (shift > 0 && startScrollLeft < shift) return 0;
```

그만큼도 밀어 두지 않았다면 사용자는 아직 그 구간을 보고 있다는 뜻이다.
열이 **줄 때**(`shift < 0`)는 따질 필요가 없다 — 보던 것이 왼쪽으로 밀리므로 언제나
따라가는 것이 옳고, 넘치면 브라우저가 0으로 잘라 준다.

이 규칙은 퇴비에서도 그대로 확인됐다. 퇴비의 숨김 열은 **275px**를 차지하는데,
200px만 밀어 둔 상태에서는 의도대로 보정하지 않는다(E2E가 이것을 먼저 실패로 알려
줬고, 시험 쪽을 실제 조건에 맞췄다).

## codex가 확인해 준 것 (문제 없음)

- 기준 열 판별은 현재 CSS 구조에서 적절하다. **모든 `thead th`가 세로 sticky**이므로
  `position`이 아니라 `left`/`right`를 보는 것이 맞다
- 좁은 화면에서 관리 열이 `position: static`이 되어도 문제없다 — 그때는 실제로 가로
  고정이 풀린 일반 열이고, 보통 첫 일반 열보다 뒤에 있어 선택되지 않는다
- 최대 스크롤 위치에서 브라우저 클램프와 보정이 정상적으로 조합된다
- 보정 → `scheduleStickyColumns` 순서가 옳다. sticky 모듈의 rAF는 보정 **이후**
  예약되므로 SLS-1-275의 latch를 재발시키지 않는다
- 토글 중 표 자체는 교체되지 않고 클로저는 핸들러가 끝나면 해제된다 — `th`를 붙들어
  생기는 누수는 없다
- 퇴비의 `const logTable` 스코프가 유효하다
- 입력·저장·권한 경로를 건드리지 않는다 — 보안 문제 없음

## codex SUGGESTION — 테스트 보완 · **일부 반영**

| 제안 | 처리 |
| --- | --- |
| `scrollLeft = 1` 같은 좌측 경계 | **반영** (유닛 2건 + E2E 1건) |
| 최대 위치에서 전체 보기 해제 | **반영** (E2E "다시 꺼도 같은 자리에") |
| 좁은 화면의 `position: static` 관리 열 | 기각 — codex 자신이 "논리적으로 문제되지 않는다"고 확인 |
| 퇴비 왕복 | 기각 — 토양에서 왕복을 덮었고 퇴비는 같은 모듈을 쓴다 |
| 목록 재렌더 직후 토글 | 기각 — 토글은 목록을 다시 그리지 않는다 |

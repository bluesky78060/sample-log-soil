# SLS-1-223 방향 — 성토 접수번호 네임스페이스 정규화

- 분류: 데이터 무결성 (운영), 우선순위 2
- 출처: SLS-1-222의 코드 리뷰 + 적대적 검증

## 목표 (Why)

SLS-1-222는 **앞으로의 가져오기**를 고쳤다. 남은 것은 두 가지다.

### 1) 두 판별자가 어긋난다 (근본 원인)

| 코드 | 시퀀스 판별 기준 |
| --- | --- |
| `reception-number.js`의 `computeNextNumber` | `subCategory === '성토'` |
| `reception-group.js` · 정렬 · 폼의 번호 파싱 | 접수번호의 `F` 접두 |

둘이 어긋난 레코드는 **두 채번 풀 모두에서 제외된다** — 일반 풀은 `F` 접두를 제외하고, 성토 풀은 구분≠성토를 제외한다. 그래서 뒤따르는 자동채번이 그 번호를 다시 부여해도 경고가 없다.

```text
H) 대장 [성토 '3'(F 없음)] / 일반 자동 ×4
   → 1, 2, 3, 4  → '3' 두 건
```

SLS-1-222의 진입점 검증은 **들어오는 행**만 막는다. 이미 대장에 있는 위반 레코드는 막을 수 없다.

### 2) 위반 레코드를 만드는 경로가 아직 열려 있다

`soil-script.js:2170-2181` `_submitSingleEdit`가 `receptionNumber`와 `subCategory`를 **폼에서 독립적으로** 받는다. 수정 화면에서 구분을 성토→논으로 바꾸면 원본 `F9`가 그대로 유지되어 위반 레코드가 만들어진다. 수정 모드에서는 접수번호 재추천도 막혀 있다.

## 사용자 (Who)
이 앱을 쓰는 기관 담당자. 특히 이미 성토 시료를 엑셀로 가져온 적이 있거나 수정 화면에서 구분을 바꾼 적이 있는 경우.

## 범위 (What)

세 부분으로 나눈다.

| 부분 | 내용 | 위험 |
| --- | --- | --- |
| **A. 탐지** | 위반·중복 레코드를 찾는 순수 함수 + 설정 화면 점검 버튼 | 낮음 (읽기 전용) |
| **B. 네임스페이스를 표기 기준으로** | `computeNextNumber`가 `subCategory`가 아니라 **접수번호 표기**로 시퀀스를 나눈다 | 중간 (채번 규칙) |
| **C. 편집 경로 차단** | 구분 변경으로 불변식이 깨지는 저장을 막는다 | 중간 (저장 경로) |

### B가 안전한 이유 — 정상 데이터에서는 no-op

불변식이 지켜지는 레코드에서는 `subCategory === '성토'` ⟺ `표기가 F로 시작`이므로 **두 정의가 같은 결과를 낸다.** 즉 건강한 대장에서 이 변경은 아무것도 바꾸지 않고, **위반 레코드에 대해서만** 동작이 달라진다 — 그것이 목적이다.

이 성질은 속성 테스트로 증명한다: 불변식을 지키는 임의의 대장에서 구/신 결과가 항상 같다.

부수 효과로 `reception-group.js`·정렬과 채번이 **같은 기준**을 쓰게 되어, 적대적 검증이 지적한 "계약이 원본 규칙의 틀림까지 복제하도록 강제한다"는 문제의 뿌리가 사라진다.

## 제약
- 운영 코드다. B는 채번 규칙이므로 폼 등록·가져오기 양쪽에 영향을 준다
- `collectExistingNumbers`(importer)는 `computeNextNumber`와 **한 줄씩 같아야** 한다 → B를 하면 양쪽을 함께 고쳐야 한다
- 적대적 검증의 지적: 그 계약에 **전수성 조건**("두 함수가 함께 커버하지 못하는 레코드가 없어야 한다")이 빠져 있다 → 이번에 추가한다
- `main`에 브랜치 보호·테스트 CI가 없다. 로컬 검증이 유일한 게이트다

## 범위 밖 — 사용자 확인이 필요하다

**이미 저장된 손상 데이터의 재번호는 이 티켓에서 하지 않는다.** 이유:
- 운영 데이터에 위반 레코드가 있는지 **코드로는 판정할 수 없다**(localStorage·Firestore에 접근 불가)
- 접수번호가 이미 라벨 인쇄·흙토람 내보내기·대장 출력에 쓰였을 수 있어, 재번호는 담당자 판단이 필요하다

대신 **A(탐지)를 먼저 제공해 사용자가 직접 확인할 수 있게 한다.** 0건이면 재번호는 필요 없다.

## 리스크
- **B가 정상 데이터에서 번호를 바꾸는 것** → 속성 테스트로 no-op을 증명한다
- **C가 정당한 수정을 막는 것** → 차단이 아니라 "접수번호를 함께 고쳐야 한다"는 안내로 처리할지 결정한다
- SLS-1-222에서 배운 것: **검증 축을 하나만 쓰면 그 축에 평행한 결함은 통과한다.** "대장 전체에 중복 0"과 "정상 데이터 no-op"을 독립 축으로 둔다

## 검증
- B: 불변식을 지키는 임의 대장에서 구/신 결과 동일 (속성 테스트, 다회 반복)
- B: 위반 레코드가 있는 대장에서 H 시나리오 중복 0
- A: 위반·중복 탐지가 실제 위반을 찾고 정상 데이터에서 0건
- C: 구분 변경으로 불변식이 깨지는 저장이 막히거나 안내된다
- 기존 단위 554건 · E2E 219건 회귀 없음 / lint 경고 기준선(4건) 유지
- **변이 검증**: 각 수정을 되돌리면 해당 테스트가 실패한다

## 방향 확정
플랜 리뷰는 **생략한다**(사용자 지시, 코드 수정). 코드 리뷰와 적대적 검증은 생략하지 않는다 — SLS-1-222에서 코드 리뷰 APPROVED 뒤 적대적 검증이 결함을 찾은 선례가 있다.

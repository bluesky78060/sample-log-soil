# SLS-1-269 Discovery — extract-whatsnew 테스트 flaky

작성일: 2026-08-21 · 사용자 승인: "모두 진행해줘"

## 1. 목표 (Why)

`tests/unit/extract-whatsnew.test.js`가 부하 상황에서 5초 타임아웃으로 **무작위 실패**한다.
무작위로 실패하는 테스트는 곧 무시되고, 무시되기 시작하면 **진짜 회귀도 함께 놓친다.**

실제로 이번 세션에서도 이 티켓 때문에 단위 테스트를 매번 **부하 없이 단독 실행**해
회피하고 있었다. 회피는 해결이 아니다.

## 2. 측정 결과 — 추정이 아니라 실측 (티켓 요구사항)

티켓이 "원인을 먼저 확인할 것, 타임아웃만 올리면 진짜 성능 문제를 덮는다"고 못박았다.

| 측정 | 값 |
| --- | --- |
| node 프로세스 기동만 | **23 ms** |
| node + `require('jsdom')` | **235 ms** |
| 테스트 1건 실제 소요 (부하 없음) | **297 ~ 381 ms** |
| 9건 합계 | 2.92 s |

→ **테스트당 비용의 약 75%가 jsdom 로드다.** 그리고 그 비용을 **테스트마다 새 프로세스에서
다시 지불한다** (`execFileSync`로 스크립트를 9번 띄운다).

우리 코드에 성능 문제가 있는 것이 아니다. **고정 기동비용 × 9회**가 CPU 경합 아래에서
5초 벽을 넘는 것이다. E2E(Chromium 5 워커)와 겹치면 300ms가 16배로 늘어나는 것은 이상하지 않다.

## 3. 범위 (What)

- `scripts/extract-whatsnew.js`를 **함수로 꺼낼 수 있게** 리팩터 (동작 불변)
- 테스트 9건 중 **8건을 in-process 호출**로 전환 → jsdom을 한 번만 로드
- **1건은 실제 프로세스 실행으로 남긴다** (아래)

### 왜 전부 바꾸지 않나

이 테스트의 가치는 **"빌드 스크립트가 실제로 동작하는가"**를 end-to-end로 보는 데 있다.
전부 in-process로 바꾸면 CLI 계약(종료 코드, `require.main` 분기, cwd 해석)이 무검증이 된다.
CLAUDE.md의 "릴리스 노트에 버전 항목이 없으면 **빌드가 실패**한다"는 규약이 바로 그 계약이다.

→ **가장 중요한 한 건(버전 누락 시 종료 코드 1)만 프로세스로 남긴다.**

## 4. 제약

- `scripts/extract-whatsnew.js`는 **빌드 필수 경로**다. 동작이 바뀌면 릴리스가 깨진다
- 리팩터 후에도 `npm run build`가 그대로 통과해야 한다
- `process.exit`를 함수 안에서 부르면 in-process 호출이 테스트 러너를 죽인다 → 결과 반환으로 분리

## 5. 우선순위

P4. 다만 **회피 비용을 계속 지불하고 있다**는 점에서 미룰수록 손해다.

## 6. 리스크

| 리스크 | 대응 |
| --- | --- |
| 리팩터가 스크립트 동작을 바꾼다 | 남긴 프로세스 테스트 + `npm run build`가 실제로 검증한다 |
| in-process 전환이 검증력을 떨어뜨린다 | 파싱·판정 로직은 그대로 같은 함수를 부른다. 잃는 것은 CLI 껍데기뿐이고 그것은 1건으로 남긴다 |
| 타임아웃만 올려 덮는 유혹 | **하지 않는다.** 원인이 구조에 있음을 측정으로 확인했다 |

## 7. 검증

- 부하를 준 상태(E2E 동시 실행)에서 단위 테스트를 **연속 5회** 돌려 전부 통과
- 리팩터 후에도 **원래 잡던 것을 여전히 잡는지**: 릴리스 노트에 버전 항목이 없으면
  빌드가 실패하는 규약이 살아 있어야 한다 → **변이 검증**으로 확인
- `npm run build` 정상

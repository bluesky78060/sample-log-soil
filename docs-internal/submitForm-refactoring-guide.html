1. 왜 분해하는가

submitForm()은 ESLint max-lines-per-function(한도 100줄) 경고가 붙은 245줄짜리 단일 메서드로, 현재 코드베이스에서 분해 ROI가 가장 높은 함수입니다.

한 함수가 3가지 완전히 다른 흐름(그룹 수정 / 단일 수정 / 신규 등록)을 모두 담고 있어, 다음 문제가 생깁니다.

  • 가독성 — 어느 분기를 읽는지 추적하려면 200줄을 위아래로 오가야 함
  • 중복 — commonData 객체 구성과 "필지×작물 채번 → 레코드 생성" 루프가 그룹 수정과 신규 등록에 거의 동일하게 두 번 존재
  • 테스트 불가 — 각 모드를 독립적으로 검증할 수 없어, 채번·동기화 회귀를 잡을 단위가 없음
  • 변경 위험 — 한 모드를 고치다 다른 모드의 로직을 건드리기 쉬움

2. 현재 구조 — 3개 모드 분기

submitForm()은 진입 직후 공통 가드를 거친 뒤, 인스턴스 상태(this.editingGroupId / this.editingLogId)에 따라 세 갈래로 분기합니다.

공통 가드 (1930–1936)
  • validParcels = 필지 주소가 입력된 필지만 필터. 0개면 토스트 후 return
  • formData = new FormData(this.form)
① 그룹 수정 모드 — this.editingGroupId 존재 1939–2031 (약 93줄)
  • commonData 객체 구성 (날짜·이름·주소·경지구분 등 12개 필드)
  • 기존 그룹 레코드 전부 제거 → validParcels.forEach로 필지×작물 채번 후 buildSoilLogRecord 호출하여 새 레코드 생성
  • saveLogs() (localStorage 먼저 — ID 할당 보장)
  • 삭제될 레코드(removedIds) 있으면 confirm — 취소 시 원본 복원 후 return (SLS-1-123 데이터 보호)
  • Firebase 삭제/저장 → filterAndRenderLogs → 백그라운드 재검증 → cancelEditMode → 목록 전환
② 단일 수정 모드 — this.editingLogId 존재 2034–2094 (약 61줄)
  • 대상 레코드 탐색(없으면 에러 토스트 return)
  • updatedLog = 기존 레코드 스프레드 + 폼 값 + parcels 재구성(인라인, commonData 미사용)
  • 첫 필지 기준 lotAddress·area·cropsDisplay 파생값 갱신
  • persistRecords → 렌더 → 백그라운드 재검증 → cancelEditMode → 목록 전환
③ 신규 등록 모드 — 위 둘 다 아님 2096–2224 (약 91줄)
  • 채번 파싱(isFillNumber·baseNumber) → 중복 접수번호 검사(같은 경지구분 1차 범위) → 중복 시 다음 번호로 교체 후 return
  • commonData 객체 구성 (그룹 수정과 거의 동일 + gongikOrder·createdAt)
  • validParcels.forEach로 필지×작물 채번 후 buildSoilLogRecord (그룹 수정 루프와 거의 동일)
  • persistRecords → 렌더 → 폼 리셋(연도·날짜·주소·필지 초기화) → 다음 접수번호 생성
  • 등록 결과 모달 표시 → 목록 전환 → runVerificationForModal
핵심 관찰 — 중복 2곳 ① commonData 객체 구성이 그룹 수정(1946) · 신규(2131)에 거의 동일하게 존재. ② "필지×작물 채번 → buildSoilLogRecord" 루프가 그룹 수정(1971) · 신규(2153)에 거의 동일하게 존재(차이는 isGroupEdit 플래그·existingLog 전달뿐). 이 두 패턴 추출이 분해의 핵심입니다.

3. 분해 설계 — 추출할 단위

목표: submitForm은 가드 + 모드 디스패치만 남기고(약 15줄), 실제 로직은 의도가 드러나는 메서드로 옮깁니다.

추출 단위입력 → 출력대체하는 중복난이도
_parseReceptionNumber(base) 'F503' → {isFillNumber, baseNumber} 1941, 2098 (순수 함수) 🟢 낮음
_collectCommonData(formData) FormData → commonData 객체 1946, 2131 🟢 낮음
_buildLogsForParcels(parcels, {baseNumber, isFillNumber, commonData, groupId, isGroupEdit, oldGroupLogs}) 필지 배열 → 레코드 배열 1971↔2153 (가장 큰 중복) 🟠 중간
_submitGroupEdit(validParcels, formData) 그룹 수정 전체 흐름 분기 ① 전부 🟠 중간
_submitSingleEdit(validParcels, formData) 단일 수정 전체 흐름 분기 ② 전부 🟢 낮음
_submitNewRegistration(validParcels, formData) 신규 등록 전체 흐름 분기 ③ 전부 🟠 중간

분해 후 submitForm의 모습

// 가드 + 디스패치만 남김 (약 15줄)
submitForm() {
  const validParcels = this.parcels.filter(p => p.lotAddress.trim());
  if (validParcels.length === 0) {
    this.showToast('최소 1개의 필지 주소를 입력해주세요.', 'warning');
    return;
  }
  const formData = new FormData(this.form);

  if (this.editingGroupId)  return this._submitGroupEdit(validParcels, formData);
  if (this.editingLogId)    return this._submitSingleEdit(validParcels, formData);
  return this._submitNewRegistration(validParcels, formData);
}

  const isFillNumber = String(base).startsWith('F');

4. 안전한 진행 순서

핫패스(데이터 저장)이므로 "안전망 먼저, 한 번에 한 조각, 동작 동치 유지" 원칙을 지킵니다.

0
폼 제출 골든 안전망 확보 (선행 필수)
분해 전에 현재 동작을 고정해야 합니다. 흙토람 빌더 골든(SLS-1-135)과 동일한 방식 — 실제 soil 페이지에서 폼+필지를 시드하고 submitForm()을 실행한 뒤, 결과 sampleLogs(접수번호·groupId 제외 정규화)를 골든 스냅샷으로 고정. 3개 모드 × 핵심 분기(단일 작물/다중 작물 채번, 성토 F, 중복 번호, 그룹 수정 삭제 confirm)를 모두 커버.
1
순수 헬퍼 추출 — _parseReceptionNumber, _collectCommonData. this 의존이 없거나 작아 가장 안전. 추출 후 골든 그린 확인.
2
모드별 핸들러로 통째 이동 — 분기 ②(단일 수정, 가장 단순)부터 _submitSingleEdit로 잘라내기. 로직은 한 줄도 바꾸지 말고 그대로 옮기는 "zero-move seam" 기법(SLS-1-106 선례). 그 다음 ①, ③ 순으로.
3
공유 루프 추출 — ①③이 분리된 뒤 _buildLogsForParcels로 중복 루프를 합치기. 가장 미묘한 단계(채번·기존 ID 보존)이므로 마지막에, 골든으로 매 단계 검증.
4
최종 확인 — submitForm이 디스패치만 남았는지, ESLint 경고 해소, 골든 + 기존 E2E(form-submission, edit-delete) 전부 그린.

5. 위험 요소와 주의점

⚠️ 채번·중복 검사 순서 변경 금지 신규 등록의 중복 검사(2112)는 localStorage에서 최신 데이터를 다시 읽어(latestLogs) 같은 경지구분 1차 범위만 비교합니다. 이 "읽기 → 검사 → return" 순서가 바뀌면 중복 접수번호가 생기거나 정상 등록이 막힙니다.
⚠️ 그룹 수정의 confirm 복원 경로 그룹 수정은 saveLogs()로 localStorage를 먼저 갱신한 뒤 confirm을 띄우고, 취소 시 원본을 복원합니다(SLS-1-123). 이 "저장 → 확인 → 필요 시 롤백" 순서는 데이터 보호 장치이므로 핸들러로 옮길 때 그대로 보존해야 합니다.
저장 메서드 차이 유지 그룹 수정은 saveLogs() + firebaseDeleteRecords/firebaseSaveRecords를 분리 호출하고, 단일 수정·신규는 persistRecords()를 씁니다. 이 차이는 "삭제 동반 여부" 때문이므로 통일하지 말 것.
✓ 동작 동치가 성공 기준 이 리팩토링은 기능 변경이 0이어야 합니다. 골든 스냅샷이 분해 전후로 한 셀도 바뀌지 않으면 성공. 바뀐다면 그것이 곧 회귀입니다.

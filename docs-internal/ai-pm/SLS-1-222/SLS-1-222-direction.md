# SLS-1-222 방향 — 성토 행 엑셀 가져오기 접수번호 결함

- 분류: **운영 데이터 무결성 버그**, 우선순위 1
- 성격: 메인 프로젝트 SAMPL-1-153과 **동일 결함의 이식 수정**

## 목표 (Why)
구분(`subCategory`)이 '성토'인 행을 엑셀로 가져오면 **전 행이 같은 접수번호로 저장**되고, 이후 일반 접수의 자동채번이 영구히 1번에 고정된다.

```text
미리보기: 1, 2, 3
실제저장: 1, 1, 1      ← 유일 1/3
저장 후 일반 다음번호: 1
```

접수번호는 이 제품의 **1차 식별자**다 — 라벨 인쇄·흙토람 내보내기·대장 출력이 모두 이 값을 쓴다. 경고 없이 중복 대장이 만들어지고 복구는 전 건 수동 재번호다.

완화: Firestore docId가 UUID라 클라우드 덮어쓰기는 없고, 목록에 즉시 보이므로 탐지는 빠르다.

## 사용자 (Who)
이 앱을 쓰는 기관 담당자. 성토 시료를 엑셀로 일괄 접수하는 경우.

## 확인된 원인 (코드 실측)

| 파일 | 문제 |
| --- | --- |
| `src/soil/soil-script.js:996-998` | `addImportedRecord`가 성토 분기 없이 일반 채번만 호출 |
| `src/soil/soil-result-importer.js:930-955` | 기존 번호 풀에서 성토를 제외만 하고 **들어오는 행의 성토 여부는 판정하지 않음** |

성토는 `F` 접두의 별 시퀀스이고 전용 함수 `generateNextFillReceptionNumber`가 `soil-script.js:956`에 이미 있으며 폼 등록 경로(`:2236`, `:4074`, `:4087`)는 올바르게 쓴다. **가져오기 경로만 빠뜨렸다.**

연쇄: 성토 행에 일반 번호 `1`이 찍힌다 → 저장된 레코드는 `subCategory='성토'`라 `computeNextNumber`가 일반 체계(`fill=false`)로 계산하며 **이 레코드를 제외한다** → 카운터가 전진하지 않아 다음 행도 `1` → 가져오기 후 일반 접수도 계속 1번.

## 범위 (What)

메인의 수정을 이식한다. **이식이 거의 그대로 된다는 것을 실측으로 확인했다** — `soil-result-importer.js`는 메인 수정 전 버전과 1,250줄 중 **49줄만 다르고, 그 차이는 CSS를 상수로·모달 HTML을 함수로 뺀 리팩터링뿐**이다. 채번 로직(`_existingNumbers`·`_recompute`·`_fns`)은 바이트 단위로 동일하다.

전제도 모두 같다:
- `src/soil/reception-number.js`의 `computeNextNumber(logs, class, {fill})` 순수 모듈 존재
- `getNextNumberForClass`가 타 연도 저장소까지 읽는 구현
- `generateNextFillReceptionNumber(landClass1)`가 `F{n}` 문자열 반환
- `STORAGE_KEY = 'soilSampleLogs'` → importer 폴백 키 `soilSampleLogs_{year}` 일치

## 제약
- 운영 코드다. 결함 경로를 정확히 고치고 회귀를 테스트로 잠그는 것이 우선
- `computeNextNumber`의 분류 규칙과 미리보기 쪽 규칙이 **한 줄씩 같아야** 한다
- **수동 번호 중복 판정은 시퀀스 무관·표기 그대로** 해야 한다 — 메인에서 이 구분을 놓쳐 회귀를 만들었다(아래 리스크 참조)
- 이 프로젝트에는 importer 단위 테스트가 없다(`tests/unit`에 `reception-number.test.js`는 있음). 메인처럼 `_fns` 노출 + 신규 테스트 파일이 필요하다

## 리스크 — 메인에서 실제로 밟은 함정

1. **미리보기만 고치고 매니저를 빠뜨리는 것.** 이 결함이 그렇게 생겼다. 양쪽 수정 후 "미리보기 번호 = 실제 저장 번호"를 시나리오별로 실측한다.

2. **중복 판정까지 시퀀스로 나누는 것.** 메인에서 자동채번용 풀을 성토/일반으로 나누면서 수동 번호의 중복 판정까지 나눠 **시퀀스 교차 충돌을 놓치는 회귀**를 만들었다.
   ```text
   대장 일반 1,2,3 + 성토 3행 수동번호 1,2,3 (기본=건너뛰기)
   올바름: dup, dup, dup → 0건 등록
   회귀:   new, new, new → 번호 1·2·3이 각각 두 건
   ```
   폼 등록 경로가 기준이다 — 중복 검사가 `logBaseNumber === numToCheck`로 **subCategory를 보지 않는다.** 시퀀스 분리는 **채번에만** 해당한다.

3. **저장되지 않는 행을 배치 집합에 남기는 것** — 건너뛰는 중복 행의 번호가 남으면 뒤따르는 자동부여 미리보기가 실제보다 앞서 나간다.

4. **약한 단정으로 또 새어나가는 것** — 이 결함은 형제 프로젝트에서 **75건이 전부 통과하는 상태로** 새어나갔다. 원인은 저장 확인이 메모리 배열만 읽고 접수번호 단정이 `not.toBe('')`뿐이었다는 것.

## 검증
- 성토만 / 일반·성토 혼재 / 수동 성토번호+자동 혼재 3개 시나리오에서 미리보기 = 실제 저장, 중복 0
- 기존 레코드(일반 `7` + 성토 `F4`) 시드 상태에서 다음 번호가 `8` / `F5`
- 시퀀스 교차 중복(성토 수동 `1` vs 기존 일반 `1`) → `dup`
- `F5` vs `5` → `new` (과잉수정 방지)
- **변이 검증** 필수 — 매니저 분기를 되돌리면 테스트가 실패해야 한다
- E2E는 새로고침 후 localStorage를 읽어 **유일성과 실제 번호값**을 정확 일치로 단정한다

## 함께 확인할 것
이미 손상된 데이터가 있는지 조회한다 — `subCategory === '성토' && !String(receptionNumber).startsWith('F')`. 있으면 재번호 절차가 별도로 필요하다. 없으면 "확인 결과 0건"을 기록으로 남긴다.

## 방향 확정
플랜 리뷰는 **생략한다** — 사용자 지시("코드 수정은 플랜리뷰하지말고 진행"). 다만 P1 데이터 무결성이므로 **코드 리뷰와 적대적 검증은 생략하지 않는다.** 메인에서 1차 코드리뷰가 APPROVED를 낸 뒤 적대적 검증이 회귀를 잡은 선례가 있다.

## codex 지적과 처리

### MAJOR — "리셋 규칙이 적용된 상태에서 레이아웃을 읽지 않는다" → **반증됨**

codex 재리뷰 주장: `sheet.textContent = buildRules(table)`가 리셋을 덮어쓴 **뒤에** 재므로
수정이 동작하지 않는다.

**사실이 아니다.** 대입의 우변(`buildRules(table)`)이 **먼저 평가**되고, 그 평가 중에
`offsetLeft`를 읽어 레이아웃이 강제된다. 이때 stylesheet에는 리셋 규칙이 걸려 있다.

말로만 반박하지 않고 실측으로 확인했다 (Chromium 1440×900, 공익직불제→농가의뢰 복귀):

```
수정 전  ③ #logTable .col-date{left:225px}  ← 틀림(자연 위치 163px)
수정 후  ③ #logTable .col-date{left:163px}  ← ①과 완전히 같음
```

변이 검증도 같은 결론이다 — **이 두 줄만 되돌리면** 왕복 시험 3건이 즉시 실패한다.

다만 **읽는 사람이 실제로 오독했다**는 사실 자체가 신호라, 평가 순서가 눈에 보이도록
한 줄씩 나눠 쓰고 그 이유를 주석에 남겼다(동작은 동일).

### MINOR — 좁은 화면 관리 열 시험이 토양만 검증 → **반영**

퇴비의 관리 열 해제 지점은 1200px다(토양은 1024px). 퇴비 1100px 왕복 케이스를 추가했다.
변이 검증으로 두 페이지 시험이 **각각** 결함을 죽이는 것을 확인했다.

### SUGGESTION — `-webkit-sticky` → **반영**

현대 Chromium은 computed value를 `sticky`로 정규화하지만, 구형 WebKit은 그대로 돌려준다.
걸러지면 **규칙이 하나도 안 만들어지는데 오류도 안 나서**(폴백 CSS로 화면은 그럴듯하다)
밀림만 조용히 되살아난다. 한 줄 비용이라 받았다.

### SUGGESTION — 강제 레이아웃 2회 비용 → **수용하지 않음(기록만)**

표당 한 프레임에 한 번만 돌고, 비용은 열 수에 비례한다(행 수가 아니다).
codex도 "실제 성능 문제가 관찰될 때 최적화할 사안"이라고 했다. 지금 최적화하면
근거 없는 복잡도만 는다.

### 문제 없음으로 확인된 것 (codex)

- 임시 `left:auto`는 `#{table.id} .sticky-col`로 한정돼 다른 표에 새지 않는다.
  두 쓰기 사이에 페인트·비동기가 없어 인쇄·다크모드로 새어 나갈 시간도 없다.
  현재 CSS에 `left: !important`가 없어 무시될 경로도 없다.
- 왕복 시험이 **규칙 문자열**을 비교하므로, 잘못된 `offsetLeft`와 잘못된 규칙이 함께
  일치해 통과하던 기존 검증의 허점을 메운다.
- `position: fixed`를 허용하면 안 된다 — `offsetLeft` 누적이 표 기준이 아니게 된다.

## 변이 검증 (적대적)

| 변이 | 결과 |
| --- | --- |
| `left:auto` 사전 무력화 제거 | 왕복 3건 실패 ✔ |
| `position !== 'sticky'` 검사 제거 | 유닛 1건 + E2E 2건(토양·퇴비) 실패 ✔ |

첫 판(좁은 화면 E2E)은 변이에서 **통과해 버렸다** — 창을 좁혀도 표 폭이 그대로면
`ResizeObserver`가 안 불려 재계산 자체가 없었기 때문이다. 시험이 결함을 놓치는 것을
변이 검증이 잡아, 재계산을 명시적으로 부르도록 고쳤다.

## 뒤집힌 결정 — (c)에서 (a)로

초안은 **(c) `farmName`·`name`만 본다**였다. 리뷰가 두 가지를 들어 기각했고 둘 다 옳았다.

### ① (c)도 여전히 죽은 분기로 남는다 ★

`buildRecord`는 행에 대표자가 없으면 **1단계 공통 대표자(`common.name`)로 메운다.**

```js
const name = getVal('name') || common.name;
```

즉 사용자가 공통 대표자를 입력하면 `record.name`이 늘 채워져 **(c)의 조건도 절대
참이 되지 않는다.** 결함이 `sampleType` 기본값 하나로 보였지만, 뿌리는

> **기본값이 적용된 `record`로 "비었는지"를 판정하는 것** 자체

였다. 필드를 하나 빼는 것으로는 못 고친다.

### ② (c)는 업무 정책을 조용히 바꾼다

"농장명·대표자 둘 다 없으면 버린다"는 **인정 범위를 좁히는** 변경이다.
리뷰가 반례를 들었다 — 접수번호·시료종류만 적고 대표자는 나중에 채우는 일괄 접수,
주소·전화로 식별하는 기존 업무 파일.

초안의 "실질적으로 잃는 정상 데이터는 없다"는 표현도 **과했다.**
정확히는 "정상으로 인정할 범위를 줄인다"이다.

→ **결함을 고치는 티켓에서 정책까지 바꾸지 않는다.** 판정 필드 3개와 문구를 그대로 두고
   **원본 셀 값**으로 보게만 바꾼다. 오늘과 달라지는 것은 **그 판정이 실제로 동작한다**는 것뿐.

## 2차 반려 — 3건 중 2건만 타당

| # | 지적 | 검증 결과 |
| --- | --- | --- |
| 1 | grep 필터 `^\S*: *//`가 주석을 못 거른다 | ❌ **틀림** — 실행해 확인했다. `soil-result-importer.js:149`가 정확히 걸러지고 실제 삭제 대상 3건만 남는다. Codex가 정규식 동작을 실행 없이 잘못 예측했다 |
| 2 | 방향 문서에 고정 숫자가 남아 있음 | ✅ 실재 — 플랜만 고치고 방향 문서를 놓쳤다. 수정 |
| 3 | "새 importer는 `.sri-*` 접두만 쓴다"가 사실과 다름 | ✅ 실재 — `active`·`is-dup`·`col-zip` 등도 쓴다. 다만 **삭제 대상 블록에 그 이름이 없어** CSS 안전성 결론 자체는 유지된다. 표현을 정정 |

2차 리뷰가 함께 확인해 준 사실:

- CSS 866-1169가 정확히 구 importer 블록이고 1170부터는 주소 컬럼 스타일이다
- 삭제 대상 블록의 정적 셀렉터는 전부 soil 구 모달 전용이다
- 동적 `.mapping-*`도 레거시 `ExcelImportManager`가 만들던 요소 전용이다
- `window.ExcelImportManager` 전역 노출은 실제 구현과 일치한다 (`excel-import-manager.js:525`)
- compost는 모듈 import와 `setupExcelImport()` 호출을 **모두 유지**한다
- 5단계 제거 검증은 현재 상태에서 DOM count 1 · 전역 function이므로 **삭제 전에 실제로 FAIL한다**
- soil의 새 importer·서식 다운로드 E2E가 **이미 존재한다**:
  `soil-importer-fill.spec.js`, `soil-import-template.spec.js`

마지막 항목 덕분에 0단계에서 새 테스트를 만들지 않고 기존 스펙을 지정하는 것으로
바뀌었다. 특히 `soil-import-template.spec.js`는 **내려받은 파일이 원본과 바이트까지
같은지**까지 본다 — SLS-1-225 사고의 재발을 막는 데 이보다 나은 감시는 없다.

## 승인 조건 (구현이 지켜야 할 것)

1. 삭제는 **6단계 순서대로** — 기준선 확인 → compost 스모크 → 코드 → 마크업 → CSS → import → 제거 검증
2. `#toastContainer`(858행)를 건드리지 않는다. 855에서 정확히 끊는다
3. CSS는 1169에서 정확히 끊는다 (1170부터 주소 컬럼)
4. `soil-result-importer.js:149`의 주석은 **남긴다** — SLS-1-225의 복구 이유를 설명하는 기록이다
5. compost 파일은 한 줄도 바꾸지 않는다
6. 5단계 제거 검증을 **삭제 전에 한 번 돌려 FAIL을 확인**한다 (순수 삭제의 변이 검증 대체)
